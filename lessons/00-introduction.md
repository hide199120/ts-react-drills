# このドリルの使い方と学び方

## このドリルのゴール

このドリルのゴールは、**「AI が書いたコードを読んで正しいか判断でき、AI が無くても基礎的なコードを自分で書ける」状態に戻すこと**です。

AI 補完を使い続けていると、「見ればわかる」けれど「白紙からは書けない」状態になりがちです。技術面接のライブコーディングや、AI の出力がおかしいときのデバッグで困るのは、まさにこの差です。

各章を終えたとき、次の3つができていれば合格です。

1. 課題のテストを、AI 補完なしで全部通せる
2. 模範解答と自分の解答の違いを説明できる
3. 章末の「面接で聞かれたら」に、何も見ずに自分の言葉で答えられる

## 1章の進め方

どの章も同じ流れで進めます。

| ステップ | やること | 目安 |
|---|---|---|
| ① 教科書を読む | この画面の「📖 教科書」。コード例は**コピペせず手で打って**試す | 20〜40分 |
| ② 課題を解く | 「✍️ 課題とテスト」で問題文を読み、エディタで `exercise.ts(x)` を編集 | 30〜90分 |
| ③ テストで確認 | ファイルを保存すると、この画面のテスト結果が自動で更新される | ― |
| ④ 答え合わせ | 全テスト合格で「💡 模範解答」が開く。自分のコードと見比べる | 10分 |
| ⑤ 口頭で説明 | 章末の「面接で聞かれたら」を、答えを開く前に声に出して答える | 10分 |

> **ポイント** 一番効くのは⑤です。説明できないところは「わかったつもり」の部分。答えを開いて、言えなかった部分だけ教科書を読み直してください。

## 準備：AI 補完をオフにする

エディタの AI 補完は、このドリルの間だけオフにしてください。VS Code + GitHub Copilot なら、`settings.json` に次を追加します。

```json
{
  "github.copilot.enable": { "*": false }
}
```

または、このリポジトリを開いたワークスペースだけで無効にしても構いません。**型の補完（IntelliSense）はオンのままで OK** です。むしろ型エラーの赤線やホバーで出る型情報は、積極的に見る習慣をつけましょう。

調べものは公式ドキュメントに限定するのがおすすめです。

- TypeScript: TypeScript Handbook（公式）
- JavaScript: MDN Web Docs
- React: react.dev（公式。「Learn」セクションは特に良質）

## テスト結果の読み方

課題画面のテストは2種類あります。

### 動作のテスト

実際にコードを実行して、結果が期待通りかを確かめるテストです。失敗すると「失敗の詳細」に、期待値（Expected）と実際の値（Received）が表示されます。

```text
AssertionError: expected 'AB-1 ' to be 'AB-1'
```

これは「`'AB-1'` を返してほしかったのに `'AB-1 '`（末尾に空白）が返ってきた」という意味です。**失敗メッセージを読む力は、実務のデバッグ力そのもの**なので、すぐに答えを見ずに読み解いてください。

最初は全部 `Error: TODO` で落ちています。これは雛形が `throw new Error("TODO")` しているためで、正常です。

### 型のテスト

TypeScript の型が正しいかを、**コンパイル時に**チェックするテストです（ファイル名が `*.test-d.ts`）。2つの書き方が出てきます。

```ts
// 1. 型が一致するか
expectTypeOf(first([1, 2])).toEqualTypeOf<number | undefined>();

// 2. 「この行はコンパイルエラーになるべき」
// @ts-expect-error 存在しないキーはエラー
pluck(users, "email");
```

2つ目は少し独特です。`// @ts-expect-error` は「次の行は型エラーになるはず」という宣言で、**エラーにならなかったら逆に失敗**します。`any` を使ってしまうと型チェックがすり抜けてエラーが出なくなるので、ここで落ちます。失敗メッセージが `Unused '@ts-expect-error' directive.` なら、「型が緩すぎてエラーにならなかった」という意味です。

## 詰まったときの手順

1. **テストコードを読む**: 課題画面下部の「テストコードを見る」。何を期待されているかが一番正確にわかります
2. **教科書の該当部分を読み直す**: 各章の「課題に入る前に」にヒントがあります
3. **小さく試す**: 関数の中で `console.log` して、値がどうなっているか確かめる（テスト実行時の出力はターミナルの `npm test` で見えます）
4. **15分考えてもダメなら模範解答を見る**: ただし見た後、**一度消して何も見ずに書き直す**こと。見て終わりにしないのが大事です

## 全体の地図

TypeScript 編と React 編は、交互に進めるのがおすすめです。React の章は TypeScript の知識を前提にしているからです。

| 順番 | 章 | 身につくこと |
|---|---|---|
| 1 | TS-01〜05 | TypeScript で日常的に書くコードの9割 |
| 2 | R-01〜04 | 画面を作るための React の基本 |
| 3 | TS-06〜08 | 型の再利用、外部データ、非同期 |
| 4 | R-05〜07 | 副作用、ロジックの分離、複雑な状態 |
| 5 | TS-09〜10 | 型の仕組みの深い理解、定番の実装問題 |
| 6 | R-08〜10 | アプリ全体の設計とパフォーマンス、総仕上げ |

> **面接では** 基礎の質問は「知っているか」より「なぜそうするのかを説明できるか」で評価されます。各章の解説は、できるだけ「なぜ」に答える形で書いてあります。

それでは、TS-01 から始めましょう。
