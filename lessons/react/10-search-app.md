# 総合: インクリメンタルサーチ

## この章で学ぶこと

この章は新しい知識はほとんどありません。これまでの章の内容を組み合わせて、**1つの画面をゼロから設計して作る**練習です。

| 使う知識 | 章 |
|---|---|
| 制御コンポーネント | R-03 |
| 値の debounce | R-06, TS-10 |
| useEffect でのデータ取得、AbortController、競合状態 | R-05 |
| 判別可能なユニオンによる状態設計 | TS-05 |
| 派生データを state にしない | R-04 |
| リストと key、条件付きレンダリング | R-01 |

「この画面を作ってください」というライブコーディングは、実際の面接でもよく出題されます。この章では、**作り始める前にどう考えるか**を中心に説明します。

## ライブコーディングの進め方

面接のライブコーディングでは、いきなり書き始めるより、次の順で進めると評価が高くなります。

1. **要件を確認する**：曖昧な点を質問する（「空文字のときは検索しない、でいいですか？」）
2. **状態を設計する**：何を state にするか、どんな状態がありうるかを先に言葉にする
3. **最小の動くものを作る**：まず debounce なしで検索だけ動かす
4. **要件を1つずつ足す**：debounce → ローディング → エラー → キャンセル
5. **エッジケースを確認する**：空文字、0件、連続入力、クリア

**考えていることを声に出しながら**進めるのが大事です。面接官は完成したコードより、考え方を見ています。

## ステップ1：要件を整理する

課題の要件を、画面の状態の視点で整理し直してみます。

- 入力欄がある
- 入力が 300ms 止まったら、trim した文字列で検索する
- 空文字なら検索しないし、何も表示しない
- 検索中は「検索中...」
- 成功したら件数とリスト、0件なら「該当なし」
- 失敗したらエラー
- 新しい検索が始まったら、前の検索は中止
- クリアボタンで入力と結果を消す

## ステップ2：状態を設計する

### どんな値が必要か

| 値 | 種類 | 理由 |
|---|---|---|
| 入力欄の文字（`text`） | state | ユーザーの入力。即座に入力欄に反映する |
| 検索に使う文字（`query`） | text から**派生**（debounce） | text が止まってから追いつく値 |
| 検索の状態 | state | idle / loading / success / error |
| 件数 | 検索結果から**計算** | state にしない |

**入力欄の値と、検索に使う値を分ける**のがポイントです。入力欄は1文字ごとに即座に反映したいけれど、検索は打ち終わってからにしたい。この2つは更新のタイミングが違うので、別の値として扱います。

### 検索の状態を型で表す

```ts
type SearchState =
  | { status: "idle" } // まだ検索していない（入力が空）
  | { status: "loading" }
  | { status: "success"; users: SearchUser[] }
  | { status: "error" };
```

TS-05 の判別可能なユニオンです。「検索中なのに結果もある」のような矛盾した状態を作れません。

### データの流れを図にする

```text
ユーザーの入力
   │ onChange
   ▼
 text（state）──────────────────→ 入力欄に表示（即座）
   │ useDebouncedValue(text.trim(), 300)
   ▼
 query（300ms 遅れて追いつく）
   │ useEffect([query])
   ▼
 searchUsers(query, signal) ──→ SearchState を更新 ──→ 結果を表示
   ↑ query が変わったら、クリーンアップで前の検索を abort
```

この図が頭にあれば、あとはそれぞれの部品を R-05、R-06 の知識で組み立てるだけです。

## ステップ3：部品ごとの考え方

### debounce

R-06 で作った `useDebouncedValue` と同じものを、このファイルの中に書きます（課題のルールで import は禁止）。

trim を debounce の前にするか後にするかで挙動が少し変わります。`useDebouncedValue(text.trim(), 300)` とすると、末尾に空白を足しただけでは query が変わらず、無駄な検索が走りません。

### 検索の effect

R-05 の形とほぼ同じです。

- query が空なら、検索せず idle にして終わり
- そうでなければ AbortController を作って、loading にして検索開始
- `.then` / `.catch` で `signal.aborted` を確認
- クリーンアップで abort

query が変わると、クリーンアップで前の検索が abort されるので、競合状態は起きません。

### 表示

状態ごとに `switch` で分岐します。件数は `users.length` から計算します。

## ステップ4：エッジケースを考える

実装が動いたら、意地悪なケースを考えます。面接官もここを見ています。

### クリア直後の問題

「田中」で検索結果が出ている状態で、「太」を追加入力し、300ms 以内にクリアを押したらどうなるでしょうか。

```text
text:  "田中" → "田中太" → ""（クリア）
query: "田中" ─────────────────────── 300ms 後 → ""
```

- text が `"田中太"` → `""` と変わるたびに debounce のタイマーは張り直されるので、`"田中太"` で検索されることはありません
- ただし、**query はまだ `"田中"` のまま**です。300ms 経つまでは、state も「田中」の検索結果（success）のまま残っています

つまり、何もしないと**入力欄は空なのに、古い結果が最大 300ms 表示され続けます**。対策はいくつか考えられます。

- クリアのハンドラで、text と一緒に検索の state も idle に戻す
- 表示の条件に「text が空なら何も表示しない」を加える（text から計算するので確実）

どちらか、または両方を使います。「text が空なら表示しない」は、R-04 の「派生データ」の考え方で、state の同期を気にせず済むので堅牢です。

### その他のケース

| ケース | 期待する動作 | どこで担保するか |
|---|---|---|
| 空白だけ入力 | 検索しない | trim してから debounce、空なら effect で早期 return |
| 素早く「田」→「田中」 | 「田」の結果は表示しない | クリーンアップで abort + aborted チェック |
| 0件 | 「該当するユーザーはいません」 | success かつ length === 0 |
| エラー後に再入力 | エラーが消えて検索中に | effect の最初で loading に |
| 入力が空でクリア | ボタンが押せない | `disabled={text === ""}` |

## アクセシビリティ

検索結果は入力に応じて動的に変わります。目が見えないユーザーにも結果の変化を伝えるには、結果エリアに `aria-live="polite"` を付けます。

```tsx
<div aria-live="polite">{/* 検索中... / 3件 / 該当なし */}</div>
```

スクリーンリーダーは、この領域の中身が変わったときに（ユーザーの操作の邪魔にならないタイミングで）読み上げてくれます。

また、入力欄は `type="search"` にすると、モバイルでキーボードの Enter が「検索」表示になるなど、意味に合った挙動になります。

## テストの読み方：フェイクタイマー

このテストでは、300ms の待ち時間を本当に待たずに済むよう、**フェイクタイマー**を使っています。

```tsx
vi.useFakeTimers(); // setTimeout を偽物に置き換える

await user.type(input(), "田中");
await act(() => vi.advanceTimersByTime(299)); // 時間を 299ms 進める
expect(searchUsers).not.toHaveBeenCalled(); // まだ呼ばれていない
await act(() => vi.advanceTimersByTime(1)); // あと 1ms
expect(searchUsers).toHaveBeenCalledTimes(1); // ちょうど 300ms で呼ばれる
```

検索結果も、R-05 と同じく「外から resolve できる Promise」で、好きなタイミングで返しています。

```tsx
await act(async () => calls[0].resolve(results)); // 1回目の検索に結果を返す
```

## 面接で聞かれたら

<details>
<summary>Q. debounce 中の値と、実際に検索に使う値を分けて持つ理由は？</summary>

更新したいタイミングが違うからです。入力欄はユーザーの入力に即座に反応しないと操作感が悪くなるので、入力のたびに更新します。一方、検索は入力のたびに実行するとサーバーに負荷がかかり、途中の文字列の結果が一瞬表示されるなどのちらつきも起きるので、入力が落ち着いてから実行したい。1つの値で両方を満たすことはできないので、入力値と、そこから debounce で派生した検索用の値に分けています。

</details>

<details>
<summary>Q. URL のクエリパラメータと検索状態を同期させるなら？</summary>

URL を検索文字列の情報源にします。初期表示時に URL の `?q=` から入力欄の初期値を読み、debounce 後の検索文字列が変わったら `history.replaceState`（または使っているルーターの API）で URL を更新します。入力のたびに pushState すると履歴が大量に増えるので replace を使います。こうするとリロードしても検索状態が残り、URL を共有することもできます。Next.js なら useSearchParams と router.replace を使います。

</details>

<details>
<summary>Q. 結果件数の変化をスクリーンリーダーに伝えるには？</summary>

結果を表示する領域に `aria-live="polite"` を付けます。中身が変わると、スクリーンリーダーがユーザーの操作の区切りで読み上げてくれます。エラーのように緊急性が高いものは `role="alert"`（aria-live="assertive" 相当）を使います。入力のたびに読み上げられないよう、debounce 後の結果だけを領域に表示するのも大事です。

</details>

## 理解度チェック

<details>
<summary>1. debounce を、query ではなく searchUsers の呼び出し（関数）にかけると何が困る？</summary>

TS-10 のような関数の debounce をコンポーネント内で使うと、レンダーのたびに新しい debounce 関数が作られてタイマーが共有されず、debounce が効きません（useRef や useMemo で保持する必要がある）。また、debounce の待ち時間中に abort やクリアの処理を差し込むのも難しくなります。値を debounce して effect で反応する設計のほうが、React の仕組みと相性が良いです。

</details>

<details>
<summary>2. 同じ検索文字列を何度も検索しないようにするには？</summary>

検索文字列をキーにして結果をキャッシュします（TS-10 の memoize と同じ考え方）。`useRef(new Map<string, SearchUser[]>())` に保存しておき、キャッシュにあればリクエストせずにそれを使います。実務では、TanStack Query がまさにこれ（queryKey ごとのキャッシュ）をやってくれます。

</details>
